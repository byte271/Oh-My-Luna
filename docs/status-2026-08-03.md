## Finding — the frozen protocol cannot measure what it claims to measure

`gate-h-heldout-v1` requires the model to return the *complete final contents* of
each file it changes. The assembled prompt contains the issue text plus, for
T1–T3, a metadata packet. It never contains the source. The transport sends
`tools: []` and `store: false`, so there is no way to fetch it and no prior turn
to draw on.

Consequence: all four arms fail for a harness reason. The continuation rule would
correctly report `no_detectable_large_signal_on_this_exploratory_corpus`, and that
sentence would be read as a finding about oracle information when it is a finding
about a missing prompt field. A true null and this defect are indistinguishable
from the summary alone.

Corroboration that the omission was accidental rather than intended:
`scripts/gate-h/forecast-cost.mjs:26-31` assumes 18,000–21,000 input tokens per
request, against an actual assembled prompt of roughly 400. The ~45× gap is the
size of the missing source, and the per-arm increments are the size of metadata
added on top of a source baseline the implementation never adds.

Five counter-arguments were constructed and all fail; they are recorded in
`research/gate-h-heldout/DEFECT-2026-08-03-unseen-source.md`.

**Established by code reading.** The detector
(`scripts/gate-h-heldout/check-prompt-completeness.mjs`) was written but could not
be executed here. Expected verdict on v1 is exit 6.

## Why nothing caught it

Every existing control verifies **integrity** — that inputs are the intended bytes
and that mutation is detected. None verified **sufficiency** — that the intended
bytes are adequate to the task posed. A 43-artifact freeze, a 10-check kernel
gate, a leakage audit, four stubs and a written runbook all passed over it.

The dry run reports 20/20 and will continue to. Its `oracle` and `noop` stubs read
the file from disk (`run-stage-a.mjs:113-129`), so they hold precisely what the
real model lacks. The stubs vary the model's *answer* while leaving the *prompt*
unexamined.

Generalized as a rule for v2: **a stub must not be more informed than the model it
stands in for**, enforced as a check rather than a convention.

## Three further problems, unblocked by the first

**Output cap.** `max_output_tokens: 8192` with whole-file output makes the cap a
function of file size, not answer length. `boltons/iterutils.py` and
`tomlkit/container.py` plausibly exceed it, which would truncate to
`response_incomplete` — another harness failure wearing a capability failure's
clothes. **Unmeasured:** the corpus is not provisioned and the freeze records no
file sizes.

**Transcription confound.** Nothing anywhere compares a returned file to the base
file (`run-stage-a.mjs:312-353`; no diff in `scripts/`). A model that fixes the bug
correctly but corrupts an unrelated function while reproducing several hundred
lines scores identically to one that never found the bug. This worsens once source
is added to the prompt, and it is plausibly asymmetric between a cheap and an
expensive model — so it would bias exactly the comparison the project exists to
make. Fix is diagnostic diff metadata that never enters the success criterion.

**Portability.** All ten `scripts/gate-h-heldout/` scripts derive the repo root via
`new URL("../..", import.meta.url).pathname`, which yields `/C:/…` on Windows and
resolves to `C:\C:\…`. Correct on the validated Linux platform; broken on the
platform this session ran on, and the RUNBOOK prerequisites never mentioned an
operating system. Reasoned from Node's `win32.resolve` semantics, **not executed**.

## Decision — sufficiency before the effort axis

The owner's directive was to pursue reasoning effort, citing a benchmark where
Luna at `max` is comparable to Sol at `medium`.

That claim is recorded as an owner assertion with its provenance gaps enumerated
(`data/provider-evidence/effort-parity-2026-08-03.json`), not absorbed into design
rationale. The repository has precedent: a documented 5:1 Luna–Sol price ratio was
falsified and is actually 25:1.

The effort axis is retained but **demoted in sequence**, because effort cannot be
measured on an instrument that returns a constant. Recorded as
`docs/adr/0016-prompt-sufficiency-before-effort-axis.md`.

Two traps found in the obvious version of the effort study:

- `max_output_tokens` bounds reasoning tokens *together with* visible output.
  Raising effort against the existing 8192 cap yields responses that terminate
  before emitting a file — measuring the cap and blaming the model.
- Crossing effort with the T0–T3 ladder gives 80 cells on 5 tasks. Rejected:
  confounded, and beyond what the frozen continuation rule can adjudicate.

Adopted instead: a single-factor study on T0 only, 5 tasks × 4 effort levels,
with **cost per success** as the primary outcome — the decision variable no
document in the repository previously framed. Capability parity with Sol would not
imply cost parity, since effort spends reasoning tokens billed at the output rate.
Cost is set from two calibration calls rather than assumed, because the existing
forecast's assumed token counts are already known wrong by ~45×.

## The first model output — and a fourth problem with the instrument

Later the same day the owner pointed at `Luna-example/`: two complete
implementations of one greenfield spec, `Luna-a` stated to have used the
Oh-My-Luna skill and `Luna-b` not. Full analysis in
`research/luna-example-framevault-ab.md`.

This is the first model output of any kind to appear in this repository.
Everything else — Gate A through H — is protocol, corpus and harness with
`live_calls_made: 0`. It arrived outside the harness, so nothing this project
built applies to it: no freeze, no leakage check, no evaluator, no receipt, no
cost record. It is a sample, and `Luna-example/` is untracked.

**Provenance is thin and is not glossed.** No file in either arm records a model
identity, a reasoning effort, a timestamp, a token count, or which skill text was
used. Which arm used the skill is an owner assertion. "Tests pass" is
self-reported by both arms and was not executed here. On the standard applied to
the effort-parity claim, this is an assertion with gaps enumerated — not a result.

What survived scrutiny, all from code reading:

- **The skill arm shipped a denial-of-service.** `Luna-a`'s decoder tracks every
  magic occurrence as a candidate and re-scans the whole live set once per input
  byte. Candidates are only ever shifted off the front, and the front cannot
  resolve until its declared range completes, so the array grows unbounded under
  attacker control. A single frame declaring a legal 16 MiB payload, filled with
  fake headers each declaring a legal length, yields ~1.2M live candidate objects
  and on the order of 10¹³ loop iterations. No declared length is oversized, so
  the spec's literal anti-allocation requirement is met and its purpose is
  defeated. `Luna-b`'s three-state machine is immune by construction: O(n), memory
  bounded.
- **The skill arm shipped a verification script that verifies nothing.**
  `typecheck.mjs` calls `stripTypeScriptTypes` on six files and prints that
  `tsconfig.json` enables strict checking. No `tsc` runs — none can, under the
  no-dependencies constraint. It exits 0 on arbitrary type errors, and the README
  lists it among the verification commands. **This is the integrity-versus-
  sufficiency defect above, reproduced independently by a model in a different
  domain, unprompted.**
- **Only the control disclosed its tradeoff.** Both recovery strategies are
  defensible — `Luna-a` recovers frames nested inside a corrupted range that
  `Luna-b` loses permanently. `Luna-b`'s README states what it gave up.
  `Luna-a`'s claims the benefit and omits the quadratic cost.

The skill arm is genuinely better on integration coverage — it has the only CLI
test and the only byte-exact wire vector — on packaging, and on configurability.
It is worse on adversarial robustness and on honest verification. Both suites have
exactly 15 tests, 13 of them the same, and each arm's two unique tests cover
something the other misses — so "better tests" overall is not supportable. On n=1
per arm with unverified provenance, none of it supports a claim that the skill
helps or hurts.

**Both defects would score as clean work.** Success is exactly
`evaluator_exit === 0`; the DoS passes every test its author wrote, and the
typecheck exits 0 by construction. The T0–T3 ladder varies information supplied,
and neither defect is caused by missing information — so §1's fix does not reach
it. This is a third confound after the missing source and the missing diff, and
it lives in the **outcome measure** rather than the prompt. Recorded as
`docs/gate-h-heldout-v2-plan.md` §8, with three options and an owner decision
owed before v2 freezes.

Two points of precision, because the loose version of this claim overstates it:

- The evaluator injects a **whole test file**, not a single test
  (`evaluate.mjs:67-92`), so same-file collateral damage *is* caught. The gap is
  narrower: defects no test in the injected file expresses — which is every
  non-functional property.
- A hang is recorded as an ordinary test failure. SIGKILL after the timeout
  (`:41`) leaves `code === null`, so the `code === -1` guard at `:96` misses and
  `:97` returns **17** — identical to a clean test failure. The one symptom by
  which a quadratic blowup could have surfaced is therefore unattributable in the
  receipts.

## Position

The project is closer to a valid first result than it was, and further from
spending money. The critical path is
`docs/gate-h-heldout-v2-plan.md` steps 1–8: entirely offline, $0.00, no credential.

The binding constraint was never the credential. Supplying one now would only make
a defective run possible.

The FrameVault sample sharpens rather than changes that. Three defects in the
instrument are now recorded — a prompt that omits the source, receipts that cannot
attribute a failure, and a success criterion that cannot express a non-functional
defect. The first two have fixes written. The third needs a decision, and it is the
owner's.
